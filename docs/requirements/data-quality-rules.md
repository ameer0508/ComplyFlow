# Data Quality & Business Validation Rules

**Project:** ComplyFlow — Compliance Workflow & Process Intelligence Platform
**Document:** Data Quality Rules & Validation Specification
**Phase:** 2B Baseline
**Validator Script:** `analytics/scripts/validate_data.py`

---

## 1. Overview & Objective

To ensure high credibility in an apprentice portfolio and prevent data corruption in Power BI and SQL, the ComplyFlow dataset enforces strict data-quality standards. Every record generated by `generate_synthetic_data.py` must pass the programmatic assertions encoded in `validate_data.py`.

---

## 2. Structural & Relational Integrity Rules

| Rule ID | Category | Assertion Description | Enforcement Level |
| :--- | :--- | :--- | :--- |
| **DQR-01** | **Record Volume** | `compliance_requests.csv` must contain exactly 150 rows. `sla_policies.csv` must contain exactly 4 rows. `request_audit_log.csv` must contain at least 1 record per request. | Critical (Fatal) |
| **DQR-02** | **Primary Key Format** | `RequestID` must be unique, non-null, and follow the exact pattern `CR-2026-XXXX` (12 characters, zero-padded integer). | Critical (Fatal) |
| **DQR-03** | **Audit Identifier** | `AuditID` must be unique, non-null, and monotonically ascending. | Critical (Fatal) |
| **DQR-04** | **Foreign Key Consistency** | Every `RequestID` present in `request_audit_log.csv` must resolve to an existing `RequestID` in `compliance_requests.csv`. | Critical (Fatal) |
| **DQR-05** | **SLA Policy Coverage** | `sla_policies.csv` must contain exactly one row for each of the four approved risk tiers: `Low`, `Medium`, `High`, `Critical`. | Critical (Fatal) |

## 3. Mandatory Fields & Completeness Rules

| Rule ID | Category | Assertion Description |
| :--- | :--- | :--- |
| **DQR-06** | **Mandatory Intake Fields** | The following attributes must **never be null or empty**: `RequestID`, `Title`, `RequestType`, `ProcessArea`, `RiskLevel`, `Priority`, `Status`, `Description`, `RequesterName`, `RequesterEmail`, `RequesterDepartment`, `SubmissionDateTime`, `TargetDueDateTime`, `SLATargetHours`, `SLABreachFlag`, `ApprovalRequired`, `CreatedDate`, `ModifiedDate`. |
| **DQR-07** | **Conditional Mandatory (Assigned)**| If `Status` is `Under Review`, `Pending Approval`, `Escalated`, `Approved`, `Rejected`, or `Closed`, then `AssignedAnalyst` and `AssignedAnalystEmail` must **not be empty**. |
| **DQR-08** | **Conditional Mandatory (Closed)** | If `Status` is `Closed`, `CompletionDateTime` and `ClosureNotes` must **not be empty**. |
| **DQR-09** | **Conditional Empty (Open)** | If `Status` is NOT `Closed`, `CompletionDateTime` must be **empty / null** (open cases are not resolved). |

| Rule ID | Field | Allowed Domain Values |
| :--- | :--- | :--- |
| **DQR-10** | `RequestType` | Strictly: `KYC Review`, `PEP Review`, `AML Transaction Inquiry`, `Sanctions Review`, `Policy Exception`. |

| **DQR-12** | `RiskLevel` | Strictly: `Low`, `Medium`, `High`, `Critical`. |
| **DQR-13** | `Priority` | Strictly: `Low`, `Medium`, `High`, `Critical`. |
| **DQR-14** | `Status` | Strictly: `Draft`, `Submitted`, `Under Review`, `Pending Approval`, `Escalated`, `Approved`, `Rejected`, `Closed`. |
| **DQR-15** | Audit `ActionType` | Strictly: `Created`, `Submitted`, `Assigned`, `Status Changed`, `Escalated`, `Approval Requested`, `Approved`, `Rejected`, `Closed`. |

## 5. Chronological & SLA Calculation Rules

| Rule ID | Rule Name | Mathematical / Logical Formulation |
| :--- | :--- | :--- |
| **DQR-16** | **Creation Chronology** | $\text{SubmissionDateTime} \ge \text{CreatedDate}$ |
| **DQR-17** | **SLA Policy Mapping** | `SLATargetHours` must exactly match the risk tier defined in `SLAPolicy`: Critical = 24h, High = 72h, Medium = 120h, Low = 240h. |
| **DQR-18** | **Deadline Determinism** | $\text{TargetDueDateTime} = \text{SubmissionDateTime} + \text{SLATargetHours}$ |
| **DQR-19** | **Completion Chronology** | For closed cases: $\text{CompletionDateTime} \ge \text{SubmissionDateTime}$ |
| **DQR-20** | **Breach Flag Truth Table** | For closed cases: $\text{SLABreachFlag} = 1 \iff \text{CompletionDateTime} > \text{TargetDueDateTime}$, else $0$. |
| **DQR-21** | **Monotonic Audit Trail** | For any given `RequestID`, all audit events must satisfy: $\text{Timestamp}_n \ge \text{Timestamp}_{n-1}$. |

## 6. Governance & Workflow Rules

| Rule ID | Rule Name | Description |
| :--- | :--- | :--- |
| **DQR-22** | **Mandatory Approval Derivation**| If `RiskLevel` is `High` or `Critical`, then `ApprovalRequired` must equal `1`. |
| **DQR-23** | **Management Sign-off Audit** | If `ApprovalRequired = 1` and case is `Closed` (favorable outcome), `ApprovedBy` and `ApprovalDate` must be populated, and a corresponding `Approved` event must exist in `request_audit_log.csv`. |
| **DQR-24** | **Escalation Consistency** | If `Status` is `Escalated`, then `EscalationFlag` must equal `1`, and `EscalatedTo` and `EscalationReason` must be populated. |
| **DQR-25** | **No Manual Resolution Time** | `ResolutionTimeHours` is forbidden from being written as a static raw column in `compliance_requests.csv`; it is reserved strictly for analytical derivation in SQL/Python/DAX. |
